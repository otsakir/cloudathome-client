# Configuration

There are two YAML config files, at different scopes:

| File | Scope | Location | Tracked in git? |
|------|-------|----------|------------------|
| `home.yaml` | Settings shared by every profile on this machine | repo root | No — gitignored, optional |
| `config.yaml` | One profile's connection to one cloud server | `providers/<profile>/config.yaml` | No — gitignored, generated by `cah.py register` |

Templates for both (`home.yaml.example`, `providers/config.yaml.example`) are
tracked in git and kept up to date with every field.

## `home.yaml`

Optional. If absent, every setting below falls back to its default. Copy
`home.yaml.example` to `home.yaml` to override any of them.

| Key | Default | Read by | Purpose |
|-----|---------|---------|---------|
| `default_cloudserver_url` | the public demo server (`http://cloudathome.retalia.org`) | `cah.py register` | Used when `--cloudserver-url` is omitted. |
| `home_console_port_base` | `8001` | `cah.py register`/`start` | Base port for auto-assigned Home Console ports — see [Portability / running several profiles at once](#portability--moving-a-profile). |
| `allowed_hosts` | `[]` | Django (`homeserver/home_config.py`) | Overrides Django's `ALLOWED_HOSTS` for every profile's Home Console. |

### `allowed_hosts` — reaching the Home Console from the LAN

With `DEBUG = True` (the default) and no override, Django only accepts requests
addressed to `localhost`/`127.0.0.1`/`[::1]` — anything else, including a LAN IP
or a local domain name, is rejected with `DisallowedHost`. Set `allowed_hosts` to
the names/IPs you actually connect with:

```yaml
allowed_hosts:
  - myhome.local
  - 192.168.1.50
```

A leading dot matches all subdomains (`.example.lan` matches `nas.example.lan`).
This must be a YAML list — either block style (as above) or flow style
(`allowed_hosts: [myhome.local, 192.168.1.50]`); a bare comma-separated string
without brackets is *not* accepted (YAML parses it as one scalar, and a malformed
value fails loudly at Django startup rather than being silently ignored).

This is a machine-wide setting, not a per-profile one — it applies to every
profile's Home Console on this box, since it's really about which names reach
*this machine*, not any particular cloud connection.

## Profile `config.yaml`

Written by `cah.py register`; see `providers/config.yaml.example` for every
field with inline comments. The fields worth calling out beyond the basics
(`cloudlink.cloudserver_url`/`auth_token`/`home_slug`/`ssh`/`ports`/`tcp_ports`,
`database`, `home_console_port`):

| Key | Default | Purpose |
|-----|---------|---------|
| `cloudlink.http_ports` / `cloudlink.https_ports` | unset | Cached copy of the cloud's default inbound port for the scheme (`default`; 80/443 when absent) and its shared alternate range (`base`/`count`). Auto-populated by `cah.py register` and refreshed by `cah.py start` on every launch — you don't set these by hand. See [forwards-and-certificates.md](forwards-and-certificates.md#custom-inbound-ports). |
| `certbot.deploy_path` | unset | After a successful certificate issuance, copy `fullchain.pem`/`privkey.pem`/`chain.pem`/`cert.pem` to `<deploy_path>/<domain>/` — useful if another service (e.g. nginx) needs the certificate outside of certbot's own directory layout. Relative paths resolve against `config.yaml`'s own directory. Overridable per domain — see below. |
| `features.lan_forwarding` | `false` | Allows a proxy entry's `home_host` to be something other than `localhost` (a LAN IP or hostname). Off by default: with it off, `home_host` is silently forced to `localhost` regardless of what's submitted in the form. Turn this on only if you actually forward to another machine on your home network. |

A `Domain` can also set its own `deploy_path` from the Home Console, which
overrides `certbot.deploy_path` for that domain only (also resolved relative to
`config.yaml`'s directory if given as a relative path).

## Registering with your own SSH key

`cah.py register` generates a dedicated SSH key pair for the new profile by
default. To bring your own instead, pass `--public-key`/`--private-key`
together (`scripts/generate_keys.py` is only needed for this path — it just
generates a standalone key pair and prints the public half to stdout so it can
be piped straight into `register`). If the automatic `manage.py migrate` step
fails after a successful registration, `cah.py register` prints the exact
command to run it yourself before starting the profile — registration itself
has already succeeded at that point.

## Removing a profile

```bash
python cah.py remove my-cloud
```

In order: disconnects all tunnels, releases the home slot on the cloud server
(which also cleans up this home's live HAProxy mappings, base domains, and
bandwidth limit server-side), revokes this profile's API token, and — only
once all of that has succeeded — permanently deletes `providers/my-cloud/`
(database, certificates, SSH key). Prompts for confirmation first; skip it with
`--yes`. If any step fails, nothing local is deleted and the error is printed —
fix the issue and re-run to retry; it's safe to run more than once.

## `HOME_CONFIG`

The environment variable that points Django at one profile's `config.yaml`.
`cah.py` sets this automatically before shelling out to `manage.py` — you only
need it yourself when scripting or debugging a single profile directly:

```bash
HOME_CONFIG=../providers/<profile>/config.yaml python manage.py runserver 0.0.0.0:8001
```

Settings are resolved from it **at Django's settings-import time** (e.g. the
database path), so `HOME_CONFIG` must already point at a valid file before
`manage.py`/`pytest` starts — there's no later point at which it can be swapped
in.

## Portability / moving a profile

Each profile's state lives entirely under its own `providers/<profile>/` directory:

| Piece | Default location | Configured by |
|-------|-------------------|---------------|
| Connection config | `providers/<profile>/config.yaml` | `HOME_CONFIG` env var |
| Database | `providers/<profile>/db.sqlite3` | `database` in config.yaml |
| TLS certificates | `providers/<profile>/certbot/` | certbot working directory |
| SSH key pair | `providers/<profile>/ssh_key` | `ssh.private_key_path` in config.yaml |

To move a profile to another machine: copy its `providers/<profile>/` directory,
update any absolute paths in its `config.yaml`, and run `python cah.py start
<profile>` as usual.

To run several cloud connections at once, just run `cah.py start` for each
profile — each auto-assigned its own port at registration time:

```bash
python cah.py start my-cloud     # e.g. port 8001
python cah.py start family-cloud # e.g. port 8002
```
